# Бот диспетчеризации заявок

Телеграм-бот для филиала сети ремонта бытовой техники. Читает заявки из CRM
bt-lead-centre.ru и уведомляет о новых.

**Этап 1 — только чтение.** Ни одного пишущего запроса в CRM код не делает.

## Что нужно заполнить перед запуском

Без этих пунктов бот не стартует и скажет об этом явной ошибкой:

1. **Учётная запись CRM** → `CRM_USERNAME`, `CRM_PASSWORD`. Вход по email.
   Лучше отдельная сервисная учётка, а не личная админская: тогда в журнале CRM
   видно, где действовал бот, а где человек, и доступ можно отозвать отдельно.
2. **Токен бота и id чатов** → `TELEGRAM_BOT_TOKEN`, `OWNER_CHAT_ID`,
   `MASTERS_CHAT_ID`, `ADMIN_CHAT_ID`, `DIRECTOR_CHAT_ID`. Токен от BotFather;
   id чата покажет команда `/chatid`. Про роли — раздел «Кто что получает».

Имена полей формы входа сняты с живой страницы 16.09.2026 и уже прописаны:
`LoginForm[email]` и `LoginForm[password]`. Страница `/admin/login` отдаётся без
авторизации, так что снять их можно обычным GET-запросом — открывать инкогнито
руками не нужно. Если платформа обновится, достаточно поправить `.env`.

## Установка на Ubuntu VPS

```bash
sudo useradd -r -s /usr/sbin/nologin btbot
sudo mkdir -p /opt/bt-dispatch-bot
sudo chown btbot:btbot /opt/bt-dispatch-bot
# выложить код в /opt/bt-dispatch-bot

cd /opt/bt-dispatch-bot
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

База:

```bash
sudo -u postgres createuser btbot --pwprompt
sudo -u postgres createdb btdispatch -O btbot
psql "postgresql://btbot:ПАРОЛЬ@localhost:5432/btdispatch" -f migrations/001_init.sql
psql "postgresql://btbot:ПАРОЛЬ@localhost:5432/btdispatch" -f migrations/002_dispatch.sql
```

Вторая миграция заводит справочник мастеров филиала из контракта. Уволенный
мастер выключен сразу. Telegram каждому мастеру администратор привязывает
командой `/master_link`.

Конфиг:

```bash
cp .env.example .env
chmod 600 .env
nano .env          # заполнить CRM_*, TELEGRAM_*, DATABASE_URL
```

## Проверка перед запуском служб

```bash
.venv/bin/python check.py
```

Проверяет по порядку конфиг, базу и вход в CRM, затем показывает, как будут
выглядеть уведомления по трём заявкам из грида. Ничего не пишет ни в базу, ни в
Telegram, ни в CRM — это безопасно гонять сколько угодно раз, пока подбираются
имена полей формы входа.

```bash
.venv/bin/python check.py --card 781594
```

Дополнительно выгружает карту полей карточки заявки. Readonly-поля в CRM идут без
атрибута `name`, их ключи заранее не известны — эта выгрузка и есть способ их
узнать. Понадобится при проектировании этапов с записью.

Тесты:

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/pytest
```

Тесты, которым нужна настоящая база, без неё пропускаются. Чтобы прогнать и их,
заведите отдельную базу и укажите её явно — боевую они трут:

```bash
sudo -u postgres createdb btdispatch_test -O btbot
psql "$TEST_DSN" -f migrations/001_init.sql && psql "$TEST_DSN" -f migrations/002_dispatch.sql
TEST_DATABASE_URL="$TEST_DSN" .venv/bin/pytest tests/test_db_integration.py
```

## Запуск служб

```bash
sudo cp systemd/*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now bt-dispatch-poller bt-dispatch-bot
journalctl -u bt-dispatch-poller -f
```

Юниты не используют `EnvironmentFile`: `.env` читает сам python-dotenv из
`WorkingDirectory`, чтобы не было расхождений в разборе кавычек.

## Как это работает

Два процесса:

- `poller.py` — раз в `POLL_INTERVAL_SEC` (60 с) читает грид открытых заявок,
  находит новые, шлёт уведомления в тестовый чат.
- `bot.py` — команды `/start`, `/ping`, `/chatid`. Кнопок на этапе 1 нет.

Только `bot.py` держит long polling Telegram; `poller.py` лишь отправляет
сообщения, поэтому конфликта getUpdates между ними нет.

**Первый запуск** делает стартовый снимок: все открытые заявки, что уже висят в
CRM, записываются как известные **без уведомлений**. Иначе первый же старт
выстрелил бы три десятка сообщений о старых заявках. Дальше уведомления идут
только о том, чего в базе не было.

**Дедупликация** — на первичном ключе `requests.crm_id`, а не на счётчике в
памяти, поэтому переживает перезапуск. Уведомление отправляется после вставки
строки; если Telegram недоступен, строка остаётся с `notified_at IS NULL` и
уходит на следующем опросе. Дубля не будет, потери — тоже.

**Разлогин** определяется по редиректу на `/` или отсутствию `.navbar` в ответе.
При детекте — релогин и один повтор запроса.

## Распределение заявок

В `SHIFT_CHECK_TIME` (09:00) бот пишет в общий чат мастеров и просит отметиться
кнопкой. **Порядок нажатий задаёт очередь на день**: кто первым поставил плюс,
тот первым получит заявку. Дальше заявки идут по кругу в этом же порядке.
Отметившийся позже встаёт в конец, а не в начало.

Директор видит новую заявку сразу, как только она появилась в CRM. **Мастеру**
она уходит за `ASSIGN_LEAD_MIN` минут до времени визита (`opened_at`) — по
умолчанию за час, не в 19:00 накануне на утренний визит. Заявки, где
администратор уже назначил мастера руками в CRM, бот не трогает.

Мастеру заявка приходит в личку с кнопкой «В пути».

Заявка уходит в **рабочий чат мастера** — у каждого свой. Личка используется
только если чат ещё не привязан.

| Событие | Что делает бот |
|---|---|
| Мастер нажал «В пути» | Статус в CRM → 4, кнопка меняется на «На месте» |
| Мастер нажал «На месте» | Статус в CRM → 8, кнопки убираются |
| Не принял за `ACCEPT_REMINDER_MIN` (5 мин) | Повторяет заявку ему же и сигналит директору; заявка пока за ним |
| Не принял за `ACCEPT_TIMEOUT_MIN` (15 мин) | Заявка уходит следующему по кругу, прежнему кнопка снимается |
| Не нажал «На месте» за `ONSITE_TIMEOUT_MIN` | Алерт администратору и директору, заявка остаётся за мастером |
| Круг пройден, никто не взял | Алерт администратору и директору, заявка ждёт |
| Никто не отметился на смену | Алерт администратору один раз за день |

Напоминание на 5-й минуте уходит один раз, а не на каждом опросе.

### Вопросы диспетчерам

У мастера две кнопки, которые спрашивают у диспетчеров:

| Кнопка | Когда появляется |
|---|---|
| 📞 Номер для дозвона | после «В пути» |
| 🏠 Запрос квартиры | после «На месте» — квартиру спрашивают, уже стоя у дома |

По нажатию бот пишет в чат диспетчеров (`DISPATCHERS_CHAT_ID`), какой мастер и
по какой заявке спрашивает. **Диспетчер отвечает реплаем на это сообщение** —
бот берёт текст ответа и пересылает его в чат мастера.

Реплай тут не прихоть: он однозначно связывает ответ с заявкой, даже когда в
чате висит несколько запросов сразу. По той же причине реплай доходит до бота
даже при включённом режиме приватности — обычные сообщения в группе бот не
видит, а ответы на свои видит всегда.

В CRM есть эндпоинт `/admin/domain/customer/get-phones`, отдающий телефон
клиента напрямую. Он читающий и доступен: вызов найден в `mainAdmin.js`, ему
нужны `cId` (id клиента) и `_serverKey` (`window.crServerKey` со страницы).
Если довести это до рабочего вида, кнопка будет отдавать номер мгновенно, без
участия диспетчеров.

Вне окна `ASSIGN_WINDOW_START`–`ASSIGN_WINDOW_END` заявки копятся и уходят
мастерам, когда окно откроется. Кнопки «Отказ» у мастера нет: отказ и переносы
оформляет администратор в CRM.

Команды администратора (работают у владельца, администратора и директора):

```
/roles                                кто сейчас владелец, админ и директор
/masters                              список мастеров и привязок
/master_link <employee_id> <tg_id>    привязать телеграм мастера
/master_off <employee_id>             выключить мастера
/master_on  <employee_id>             включить обратно
```

Свой `tg_id` мастер узнаёт командой `/chatid`.

## Отчёт мастера и проведение заявки

Кнопка «📋 Отчёт» появляется у мастера после «В работе». Анкета идёт в таком
порядке: фото БСО и чека СМЗ → есть ли ЗПЧ → фото ЗПЧ → режим чека →
предоплата → сумма заявки → сумма ЗПЧ → отзыв. Документы просим первыми,
пока мастер ещё у клиента и может переснять; суммы — в конце, когда посчитано.

Отдельного вопроса «БСО есть?» нет: ответ виден по тому, прислал мастер
снимки или нажал «Готово» пустым. Снимок удаляется из чата сразу, как попал
в базу, а счётчик принятых дописывается в сам вопрос — чат мастера остаётся
чистым.

Шаг и все ответы живут в строке таблицы `closures`, а не в памяти процесса:
перезапуск службы посреди анкеты ничего не теряет.

Сводка уходит администратору и директору с кнопками «Провести» и «Отклонить».
Странности (ЗПЧ дороже заявки, предоплата больше суммы, нет фото БСО) выводятся
в сводке предупреждением, но проведение не блокируют — решает человек.

**Отклонение сбрасывает отчёт целиком.** Мастер проходит анкету с нуля, а фото
забракованного отчёта остаются в базе историей и в CRM не попадают: иначе
отклонённый снимок уехал бы в карточку вместе с исправленным.

Проведение в CRM — два POST подряд на карточку заявки, под блокировкой по её
номеру. Перед ними каждое фото уходит отдельным ajax на `image-upload`.

1. вся форма карточки + скрытое `save_close=1` — без него Yii не записывает
   нули, «Нет» и отзыв;
2. та же форма на `...&finish=1` — это и есть кнопка «Провести заявку»,
   отдельного экшена у неё нет.

После записи карточка перечитывается: проверяется, что задуманные поля легли,
что соседние не задеты и что статус стал «Готов». Расчёт мастеру отправляет
поллер тем же механизмом, что и раньше.

Повторное «Провести» безопасно: решение меняет состояние отчёта до записи, на
карточку берётся блокировка, а уже проведённую заявку бот распознаёт по статусу
и не трогает. Если CRM отказала — отчёт цел, проверяющие получают текст ошибки
и кнопку «Повторить проведение», мастер заполнять заново не должен.

## Кто что получает

Три роли, и они не пересекаются. Владелец филиала ничего не подтверждает —
он видит, что происходит. Решения принимают администратор и директор.

| Что | Владелец | Администратор | Директор |
|---|---|---|---|
| Лента заявок: пришла, ушла мастеру, передана, расчёт отправлен | да | — | да |
| Шаги мастера: в пути, на месте, в работе, отчёт сдан, закрыто в CRM | да | — | — |
| Отчёт на подтверждение с кнопками | — | да | да |
| Рабочие тревоги: просрочка, нет свободных, не отметились на смену | да | да | да |
| Сбои бота и CRM — сразу, как случились | да | — | — |
| Сводка сбоев за сутки в 21:00 | да | — | — |
| Итоги дня в 22:00 | да | — | да |

Отчёт уходит администратору и директору одновременно: кто первым нажал
«Подтвердить» или «Отклонить», тот и решил, у второго кнопки гаснут. В ленте
владельца видно, кто именно решил.

### Сводка сбоев в 21:00

О сбое владелец узнаёт сразу, но одинаковые сообщения схлопываются, а поток
ограничен дюжиной в час: заваленный чат читают так же, как журнал сервера.
Поэтому каждый сбой ещё и складывается в таблицу `failures`, а в
`FAILURE_REPORT_TIME` (21:00) владельцу уходит сводка за сутки — включая то,
о чём промолчали.

Период считается от прошлой сводки, а не от полуночи: иначе сбои между 21:00
и полуночью не попали бы ни в одну. Тихие сутки — тоже сообщение: «всё
штатно, сбоев не было».

К каждой причине идёт совет, что делать. Классы сбоев и советы лежат рядом в
`reporting.py` (`CATEGORIES` и `FIXES`) — тест не даёт завести класс без
совета. Владелец не разработчик, имена исключений остаются в `journalctl`.

Администратор задан в `.env` как `ADMIN_USERNAME` (без собачки). Написать
человеку по одному @username Telegram не даёт, поэтому `chat_id` бот ловит
с первого сообщения администратора боту и кладёт в `app_state` —
перезапуск службы его не теряет. Пока администратор не написал, отчёты идут
по `ADMIN_CHAT_ID` из `.env` и директору. Проверить — команда `/roles`.

## Модули

| Файл | Ответственность |
|---|---|
| `crm.py` | Единственное место, знающее про HTML и URL CRM. Отдаёт `RequestRow` / `RequestCard` |
| `db.py` | Доступ к PostgreSQL |
| `config.py` | Параметры из `.env` с проверкой обязательных |
| `dispatch_queue.py` | Очередь дня и выбор следующего мастера |
| `messages.py` | Тексты и клавиатуры, общие для обоих процессов |
| `poller.py` | Цикл опроса, распределение, таймауты, алерты |
| `bot.py` | Кнопки мастера, отметка смены, команды администратора |
| `roles.py` | Кто что получает: владелец, администратор, директор |
| `check.py` | Диагностика связности перед запуском, только чтение |

У платформы есть закрытый REST API (п. 7 контракта). Если филиал получит токен,
переписывается только `crm.py` — остальной код работает с доменными объектами.

## Защита боевой CRM

`CRM_READ_ONLY=true` по умолчанию. **Пока флаг включён, в CRM не уходит ни один
пишущий запрос**: назначение мастера и смена статуса пишутся в базу бота и
показываются мастеру, а в CRM только логируется намерение. На это есть тест —
`test_read_only_не_отправляет_ни_одного_post`.

Вся запись идёт через единственную точку `CrmClient._post_write`. Запись —
обязательно read-modify-write: CRM принимает форму карточки целиком, поэтому
частичный POST затёр бы остальные поля. Readonly-поля формы (тип техники, дата
заявки) уходить в POST не могут — у них нет атрибута `name`.

Снимать флаг имеет смысл только после проверки на непроизводственной заявке.
Пока он включён, бот для CRM — обычный читатель.

POST уходит только при аутентификации на `/admin/login`.

## Не снято с CRM (п. 9 контракта)

1. Имена полей формы входа — **снято 16.09.2026**: `LoginForm[email]`,
   `LoginForm[password]`, плюс галочка `LoginForm[rememberMe]`, которую бот
   выставляет, чтобы сессия жила дольше.
2. Параметры `get-updates` — не нужны, опрос идёт по гриду.
3. Механизм проведения заявки — нужен для закрытия заявок, этап 2 не закрывает.
4. Коды статусов кроме 1/4/8/9/64 — бот пишет только 4 и 8, они известны.
   Заявки бот различает по тексту статуса из грида, этого хватает.

## Расхождение с контрактом

Контракт утверждает, что грид без фильтра отдаёт только открытые заявки. **Это
не подтвердилось.** Проверка на живой CRM 16.09.2026: из 35 строк 7 были в
статусе «Готов», по одной — «Отказ» и «Отмена Филиала».

Поэтому активность заявки определяется статусом, а не фактом присутствия в
гриде. Списки статусов — в `.env`:

- `ACTIVE_STATUSES` — по ним работают таймеры и считается, что заявка жива
- `ASSIGNABLE_STATUSES` — только их бот раздаёт мастерам

Перечислены именно незакрытые статусы, а не закрытые: незнакомый статус тогда
считается закрытым, и бот по нему ничего не делает. Это безопаснее — ошибка в
списке приведёт к молчанию бота, а не к раздаче мастерам отменённых заявок.

## Известное ограничение

Если заявка успеет появиться и уйти из грида между двумя опросами (60 с), бот её
не увидит. Это свойство источника данных, а не кода; обходной путь не
закладывался без решения заказчика.
